# TDLib Media Uploader

把本地或 SMB/NAS 目录中的视频和图片批量上传到 Telegram 超级群话题或频道。上传由内置 TDLib 完成，无需打开 Telegram Desktop。支持逐组预览和编辑标题、后台扫描、持久化任务队列、断点恢复与独立代理。

## 安装与登录

| 平台 | 安装方式 |
| --- | --- |
| Windows x64 | 下载 ZIP，完整解压到可写目录，运行 `TDLib Media Uploader.exe`。 |
| macOS 14 及以上，Apple Silicon | 下载 arm64 DMG，把 `TDLib Media Uploader.app` 拖到“应用程序”。 |

安装包内置运行环境、LGPL FFmpeg 和 FFprobe，无需另装 Python。用户运行入口是发布包，源码用于开发、离线测试和构建。macOS 包未配置 Apple Developer 签名和公证，首次启动可能出现 Gatekeeper 提示。发布包支持 `--self-test`，首次登录前即可检查资源、数据目录写权限、TDLib 路径和内置媒体工具。

从本仓库的 Releases 下载文件并核对 `SHA256SUMS`。Windows 可用 PowerShell 的 `Get-FileHash <文件名> -Algorithm SHA256`，macOS 可用 `shasum -a 256 <文件名>`，将结果与清单中同名文件的摘要比较。两个安装包都下载时，可在 macOS 将它们与清单放在同一目录，执行 `shasum -a 256 -c SHA256SUMS`。

1. 在“设置与诊断 → Telegram”填写并保存 API ID 和 API Hash。凭据可从 [Telegram 开发者页面](https://my.telegram.org/) 获取。
2. 打开“媒体上传”，选视频、图片或混合模式，点击“选择目录”和“修改目标”。超级群话题填写群组 Chat ID 和话题 ID，频道填写频道 Chat ID。三种模式可以使用不同目标。登录账号需要具备向所选目标发送媒体的权限。
3. 扫描目录，核对分组、文件和标题，然后点击“加入上传队列”。可选“加入并前往任务中心”或“加入并继续扫描”。
4. 首次连接时按提示完成登录。Telegram 可能要求手机号、验证码、两步验证密码或已登录设备确认。任务中心会显示发送进度、速度、剩余时间和日志。

连续任务共用已登录的 TDLib 会话。网络中断时，队列等待连接恢复后再提交新的 Album。空闲时可在任务中心点击“断开 Telegram”。

## 扫描和预览

- 图片预览为“媒体组 → 文件”。视频按月份分组时为“月份 → 媒体组 → 文件”。混合上传为“文件夹 → 媒体组 → 文件”。展开组查看完整成员，悬停标题或状态可查看完整说明。
- 搜索可匹配文件名、路径和标题。“只看待上传”隐藏已完成、已跳过及本次排除的条目。**筛选仅改变视图，入队范围由原有清单和排除操作决定。**
- 双击组标题或点击“编辑标题”，可以修改基础标题及追加文本，并实时预览多行 Caption。图片保留配置中的编号规则。
- 用“跳过该组 / 恢复该组”排除或恢复本次要入队的 Album。预览会同时保留真实投递状态，例如“失败 · 已排除”。已经入队的任务、上传断点和未确认保护记录照常有效。
- 上传时仍可扫描其他目录、编辑标题和入队。同一时间最多运行一次扫描和一次上传。更改来源或目标后请重新扫描并核对预览。

侧栏按钮切换深浅主题，偏好在下次启动时恢复。程序成功解析 Telegram 目标后会缓存群组和话题名称。显示名称用于辨识目标，发送依据仍是 Chat ID 和话题 ID。

## 媒体规则

### 分组、排序和标题

| 选项 | 视频 | 图片 | 混合 |
| --- | --- | --- | --- |
| 扫描范围 | 来源目录及子目录 | 来源目录及子目录 | 每个一级子文件夹及其子目录 |
| 默认分组 | 按媒体日期归入月份，可改为按扫描顺序固定分组 | 按扫描顺序分组 | 每个一级子文件夹独立分组 |
| 默认排序 | 文件修改时间 | 文件修改时间 | 文件夹和文件名自然排序 |
| 默认标题 | 月份或 Album 编号，可隐藏组标题 | 可开启或关闭 Album 编号 | 一级文件夹名称，可追加文字 |

每组可设为 1–10 个文件，超出时拆成多个 Album。剩余文件不足一组时也会发送，只有一个文件时发单条消息。标题附在组内第一条实际发送的消息上。可在标题后附文件名清单，并独立开关序号。文件名清单去掉最后一个扩展名，例如 `clip_a.mp4` 显示为 `clip_a`。

自然排序逐层比较路径，连续数字按数值排序，例如 `Day2/x.10.jpg`、`Day2/x.100.jpg`、`Day10/x.1.jpg`。改用修改时间排序时，时间相同的文件仍按路径稳定排序。混合根目录直接放置的媒体会被忽略，需移动到一级子文件夹。

### 视频格式与大小

- 默认扩展名为 `.mp4`、`.mov`、`.m4v`、`.mkv`、`.avi`、`.ts`、`.mts`、`.m2ts`。扫描也会识别常见实际容器，准备时以 FFprobe 探测结果为准。
- 原生 MP4、MOV、M4V 中的 H.264 或 HEVC/H.265 视频可使用原文件或本地暂存副本直传。该路径无需生成重新封装的 MP4。
- 默认 `compatibility_policy = "remux"`。需要处理的视频会尝试用 FFmpeg 流复制为 MP4，并验证容器和音视频编码。源文件不改写，音视频不重新编码。若 MP4 无法承载原编码，任务会显示准备失败原因。成功封装也不代表 Telegram 播放端一定支持原编码。设为 `"original"` 时，仅采用兼容的原生直传路径。
- 重新封装的副本位于 `data/cache/video_processed/<组>/`。例如 `clip.ts` 生成 `clip.mp4`，同组发生同名冲突时可用 `clip.ts.mp4` 和 `clip.avi.mp4` 区分。整组确认并保存断点后会清理已处理副本，待核对的制品可保留供恢复。
- 程序检查实际待上传的视频大小。普通账号单文件上限为 `2,097,152,000` 字节，Premium 为 `4,194,304,000` 字节。介于两者之间的文件在登录后按账号状态复核，超过 Premium 上限的文件会提示原因。

### 图片格式与大小

默认支持 JPEG、PNG、静态 WebP、BMP 和 TIFF，对应 `.jpg`、`.jpeg`、`.png`、`.webp`、`.bmp`、`.tif`、`.tiff`。程序按 Telegram Photo 规则检查宽高之和不超过 `10000`、长宽比不超过 `20`、单文件不超过 `10 MiB`。需要处理时，长边目标为 `2560` 像素，压缩目标为 `9.5 MiB`。

处理结果保存在缓存。BMP、TIFF 和静态 WebP 可转为 JPEG，透明区域使用配置的背景色（默认 `#FFFFFF`）。超长图片默认填充画布，可设置 `extreme_aspect_policy = "skip"` 改为跳过。动画、损坏或无法规范化的图片会显示预检结果，上传使用媒体消息类型，不会自动改为普通文件发送。

升级会保留旧的 `data/config.toml`。旧配置中缺少的扩展名，可对照[配置模板](resources/default_config.toml)补入 `[video].extensions` 或 `[image].extensions`。两类扩展名需互不重复，混合模式继承这两份列表。

### 日期和视频封面

视频的默认日期来源依次为 EXIF、可选的媒体创建日期、文件修改时间。ExifTool 批量处理已扫描到的文件，缺少可用日期时可通过 FFmpeg 读取媒体创建日期。ExifTool 为可选工具，下载后可在“高级选项”指定路径。 [ExifTool 官网](https://exiftool.org/)

- 关闭 `read_media_creation_date` 可省去媒体日期回退。默认 `missing_date_policy = "mtime"` 回退到文件修改时间，设为 `"error"` 时缺失日期会提示处理。
- 只想按文件名上传时，关闭 `[video].read_dates`。程序会按文件名自然排序和固定数量分组，仍会记录文件快照供发送前复核。
- 视频及混合模式的缩略图默认从 `1.00` 秒截图。可分别调整 `[video]` 和 `[mixed]` 的 `thumbnail_timestamp_seconds`，支持 `0.01` 秒精度。旧配置中混合模式缺省时继承视频值。修改后如仍看到旧封面，可在“存储与缓存”点击“仅清理视频封面缓存”。

## 队列与恢复

任务中心顶部常驻上传进度，左侧是队列，右侧可在 Album 明细和实时日志之间切换。点击列表中的 Album 查看文件和处理原因。

入队时会保存媒体配置、来源、目标、完整成员及顺序、文件大小和修改时间以及最终 Caption。后续草稿修改只影响新任务。执行前会重新核对源文件和断点，已确认文件会跳过。相同类型、来源和目标下，重叠的任务范围无法同时排队。

| 操作 | 行为 |
| --- | --- |
| 暂停队列 | 暂停启动下一项，正在执行的任务可以继续。 |
| 安全停止 | 等当前正在发送的 Album 得到结果并保存断点后停止。正在准备、尚未提交的组不会开始发送。 |
| 立即中断 | 尽快停止传输。已提交且结果无法确认的组会留待人工核对。 |
| 上移、下移、置顶、移除 | 用于管理等待中的任务。 |
| 清理已结束 | 移除队列中的已完成和已跳过任务，失败、中断和待核对任务留待处理。 |

重启后队列默认暂停。异常退出时，程序会结合已保存断点和发送记录区分“已中断”和“待核对”。待核对任务会阻止后续任务启动。

### 失败、中断和人工核对

1. **失败或中断，可重新验证。** 在任务中心选择“重新验证并恢复”。检查通过后任务回到原位置，保留原目标、组序和标题。点击“继续队列”后从未确认完成的文件续传。文件被替换或清单失效时，按提示重新扫描。
2. **只处理某个 Album。** 明确在提交前失败，或整组明确被拒绝或发送失败，可选“重试该 Album”。如果部分投递成功，解除保护后可选“仅重试失败文件”。一次 Album 重试完成后，其余待发送组仍留在原任务。
3. **存在待核对记录。** 在 Telegram 中检查实际目标与组内文件，再到“未确认上传”选择“标记为已发送”或“允许重新上传”。部分成功时，已确认文件保留断点，只会恢复尚未确认的成员。旧记录缺少可靠对应关系时会保留保护。如果磁盘源文件已经变化，人工核对可以保存结果，预览需重新扫描。
4. **跳过整个失败或中断任务。** “跳过此任务”会先校验清单、目标、未确认记录和已确认断点。只要这些记录可验证，即使来源已离线也可以跳过。任务与历史会显示“已跳过”。

恢复、跳过和核对可在后台检查。取消检查时，已经开始的持久化操作会完成。恢复或跳过后，通过“继续队列”重新开始调度。

暂时不可读的文件显示为“暂缓”。预检或发送前快照变化不会让后续文件向前补位。默认严格顺序模式可在准备失败、暂缓、提交失败或结果未确认时停下，避免后续 Album 插队。消息已经提交后的超时、断线、中断和部分成功会留待人工核对，自动重试不会绕过这层保护。

## 配置与性能

首次运行会从[配置模板](resources/default_config.toml)创建 `data/config.toml`。日常可通过“设置与诊断”编辑，配置错误时界面会提示。视频、图片和混合可分别配置 `[telegram.video]`、`[telegram.image]` 和 `[telegram.mixed]`，不单独配置时继承 `[telegram]` 的公共目标。

| 设置入口 | 常用选项 |
| --- | --- |
| 常规 | 来源目录、本地暂存模式、目录及清理周期。 |
| Telegram | API 凭据、代理和实验性远程预上传。代理默认关闭，支持 SOCKS5、HTTP 和 MTProto。 |
| 上传参数 | 各模式的目标、排序、分组、标题、封面和有界预取。 |
| 高级选项 | 本地与网络 I/O 并发、文件稳定性、ExifTool 路径、处理超时、Album 重试和限流。 |
| 存储与缓存 | 缓存上限、清理入口、数据目录和日志位置。 |

SOCKS5 和 HTTP 可填写用户名和密码。MTProto 使用十六进制 Secret。

### 本地暂存与预取

- `[staging].mode` 可设为 `off`（默认，直接读取源文件）、`network`（仅暂存识别出的网络盘文件）或 `always`（暂存所有文件）。Windows 可使用 UNC 路径，例如 `\\server\share`。暂存副本默认放在 `data/cache/staging/`，断点以原始路径为准，程序只清理受管副本。默认启动清理超过 7 天的暂存文件，成功后的清理可单独设置。
- `[upload]` 默认启用预取，最多准备 3 个 Album，按源文件大小预留 8 GiB。字节预算包含正在发送的已准备组。超过整个预算的单组轮到时再准备。关闭预取后按组准备和发送。暂停或中断会回收尚未发送的预取暂存副本。
- `[scan]` 分别设置本地和网络盘的稳定检查、间隔及 I/O 并发。默认本地并发 4、网络并发 2。扫描会跳过链接和 Windows junction，正在执行的系统文件调用返回后才会响应取消。
- `[process]` 设置 ExifTool 批次、重试和媒体工具超时。ExifTool 默认批次 256 个，FFmpeg 封面提取默认超时 45 秒。

### 限流与重试

默认整组自动重试关闭。开启后，明确可重试的拒绝和整组失败共享 `max_retries` 额度，默认额外 2 次，可设置为 1–10 次。等待取 `retry_delay_seconds`（默认 1 秒）与 Telegram 要求的较大值，重试前会再次核对发送记录和文件快照。关闭整组重试时，明确的 FloodWait 仍可按 `flood_max_retries` 单独重试，默认额外 1 次。续传时，只有本次提交的剩余项均明确因限流失败，才会重试这些文件。

- `queue_error_policy = "pause_on_error"` 为默认的严格顺序策略。`"skip_and_retry"` 可先处理后续 Album，再用已开启的整组重试额度中的最后一次机会处理明确失败且可重试的组。该模式下，`pause_on_unknown` 默认在遇到未确认组时暂停当前任务。设为 `false` 时可继续处理当前任务中符合条件的后续 Album，仍保留未确认保护。
- `min_send_interval_seconds` 控制 Album 间最小发送间隔，`flood_jitter_seconds` 为限流等待附加随机间隔。任务中心显示尝试次数和倒计时，可以用安全停止或立即中断取消等待。
- 可选的 `[tdlib].enable_preliminary_upload` 默认关闭。启用后按 `max_concurrent_file_uploads` 并发准备主照片和视频，默认并发 4，缩略图仍随消息本地发送。持续没有字节进展超过 `preliminary_wait_seconds` 时回到直传，默认 30 秒。若预上传引用被拒绝，只有确认本次提交均未送达时才会改用本地文件。提交前取消只中断预上传。

直接上传期间请保持源文件不变，TDLib 会异步读取文件。对于还在写入的共享目录，启用本地暂存可在文件通过稳定检查后固定待发送副本。

## 数据备份与维护

| 平台 | 数据目录 |
| --- | --- |
| Windows | `TDLib Media Uploader.exe` 同目录下的 `data/` |
| macOS | `~/Library/Application Support/TDLib Media Uploader/data/` |

升级或搬迁时先**完全退出应用**，再备份并复制整个 `data/` 到新安装的对应位置，避免形成 `data/data/`。2.0 通过 SQLite WAL 保存队列、上传断点、未确认记录和媒体探测缓存。首次读取时自动导入 V1.9 的 `upload_queue.json`、`state/` 和 `upload_inflight/`，原始 JSON 保留作备份。登录数据库仍位于 `data/telegram/database/`。应用持有 `data/app.lock`，同一数据目录只能由一个实例使用。

```text
data/
├── config.toml          # 配置与代理
├── uploader.db          # 队列、断点、未确认记录、媒体元数据
├── telegram/
│   ├── database/        # TDLib 登录数据库
│   └── files/           # TDLib 文件缓存
├── captions/            # Album 标题
├── ui_preferences.json  # 主题偏好和 Telegram 目标名称
├── cache/               # 封面、压缩、重新封装和暂存副本
├── logs/                # app.log、tdlib.log
└── history.json         # 最近 100 条任务记录
```

“存储与缓存”可分别清理视频封面和重新封装的视频，也可清理所有缓存与断点。后者清除断点、标题、历史和处理缓存等，保留配置、登录会话及未确认保护。各上传页的“重置断点”只清除当前媒体类型的全部断点，包括该类型的其他来源与目标。**清理断点后，原已确认文件可能再次显示为待上传。继续发送前请核对，避免重复上传。**

默认封面缓存上限为 512 MiB，压缩图片为 2048 MiB，媒体探测结果最多保留 50,000 条。封面和压缩图片会在启动及任务结算后按最近使用时间清理，待核对任务的制品可保留。缓存清理可在后台取消。

`config.toml` 可能包含明文 API Hash 和代理凭据，`telegram/` 保存会话。`logs/app.log` 用于查看应用运行与失败原因，`logs/tdlib.log` 保存 TDLib 诊断。分享日志或截图前，请遮盖凭据、本地路径和目标 ID。Windows 可在“环境与许可”查看数据目录的读取权限诊断。

## 开发与构建

源码使用 Python 3.13 和锁定的 `tdjson 1.8.71`。将 FFmpeg 与 FFprobe 加到 `PATH`，在仓库根目录运行本地离线检查。

```bash
python -m pip install -r requirements-build-lock.txt -r requirements-test.txt
python -m compileall -q src tests
PYTHONPATH=src QT_QPA_PLATFORM=offscreen python -m pytest tests -q
```

测试覆盖队列恢复、文件快照、模拟投递、Qt 界面和合成媒体的实际 FFmpeg 处理。离线测试和发布包的 `--self-test` 可在没有 Telegram 登录的环境运行。真实上传及对账可在打包应用中使用测试目标验证。

[GitHub Actions](.github/workflows/build-platforms.yml) 在 Windows x64 和 macOS arm64 上先执行离线回归和源码自检，再通过 [PyInstaller 配置](tdlib_media_uploader.spec)打包并校验媒体工具、许可、图标和包内自检。macOS 的 FFmpeg 缓存键包含源码校验和、平台、架构及构建工作流摘要，未命中时会重新编译。发布包仅包含应用及所需资源，测试、个人配置、登录数据和本地断点都留在包外。

程序从 [`VERSION`](VERSION) 读取版本号。推送 `main` 会执行构建检查，推送与版本一致的 `v` 标签会发布 Windows ZIP、macOS DMG 和 `SHA256SUMS`。发布变化见[更新记录](CHANGELOG.md)。
